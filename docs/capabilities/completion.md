# Автодополнение кода

Контекстные подсказки по мере ввода: глобальные функции, методы и свойства объектов (с выводом типа), типы после оператора `Новый`, ключевые слова и локальные переменные.

**Горячие клавиши:** `Ctrl+Space`

[← Все возможности](index.md)

## Отбор и приоритет по контексту компиляции

При известных метаданных предложения отбираются и упорядочиваются с учётом текущего модуля, директивы метода и ветки препроцессора. Для проекта используются автоматически выбранные режимы конфигурации и общая настройка `supportThickClientFileMode`. По умолчанию заведомо недоступные варианты скрываются. Сначала идут доступные варианты, затем доступные лишь в части возможных контекстов.

Отбор управляется настройкой в `.bsl-language-server.json`:

```json
{
  "completion": {
    "hideUnavailableByContext": true
  }
}
```

При `false` недоступные варианты тоже показываются, в конце списка. Изменение применяется со следующего запроса completion.
Предложение скрывается, только если оно заведомо недоступно во всех текущих контекстах и для всех возможных целей.
Частичная доступность и неизвестные сведения не приводят к удалению предложения.

Порядок учитывает доступность платформенных членов и типов из СП, видимость общих модулей, условия объявлений прикладных методов и разрешённые серверные переходы. Поэтому серверный метод с разрешённым вызовом с клиента сохраняет обычный приоритет в клиентском коде.

Прикладные типы наследуют доступность базового типа из СП, например `ДокументМенеджер.<Имя документа>`.
У общих модулей учитываются флаги метаданных ещё до разбора файла. Глобальные свойства, включая `Справочники`,
ранжируются по собственной доступности и доступности типа значения.

После точки учитывается контекстный тип получателя. Если разные ветки `#Если` присваивают переменной разные структуры, повторная проверка того же условия выбирает соответствующий тип: поля исключённого типа не предлагаются. К членам оставшегося типа применяется тот же отбор по контексту; при выключенном отборе недоступные члены сохраняются с пониженным приоритетом.

Внутри групп сохраняются прежние приоритеты локальных имён, полей, глобальных функций и ключевых слов, а также порядок устаревших элементов. Недостаток сведений о доступности не понижает предложение. В OneScript, без метаданных или при неизвестном контексте сохраняется прежняя сортировка.

## Контексты методов и серверные вызовы

Справа от сигнатуры метода показывается только пометка серверного вызова перед возвращаемым типом, например `→С · ТаблицаЗначений`.
Имя, сигнатура и вставляемый код сохраняются. Язык подписи соответствует варианту встроенного языка проекта,
как имена платформенных методов и типов; язык сообщений диагностик задаётся отдельно языком сервера.

| Пометка | Значение | В английском проекте |
| --- | --- | --- |
| `→С` | Из текущего места требуется переход на серверную сторону | `→S` |
| `→С?` | Переход зависит от режима или выбранной цели вызова | `→S?` |

Контексты компиляции и пояснение вызова добавляются обычным текстом под описанием метода,
в том числе после отложенной загрузки документации. Отдельного заголовка в поле `detail` нет.
Переход рассчитывается по текущей директиве и ветке препроцессора:
у серверного метода при вызове с сервера стрелки нет. Файловый локальный вызов общего модуля не считается
серверным переходом. Переход между частями формы не означает обязательного сетевого обмена.
Доступность платформенного метода из СП сама по себе не доказывает наличие серверного вызова.
При неизвестном контексте и в OneScript пометки не добавляются. Клиенты без поддержки подписи справа
получают краткую пометку в обычном поле деталей после сигнатуры и типа.
