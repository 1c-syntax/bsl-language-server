# Пул задач упорядочивания архитектуры

Найденная архитектурная энтропия, ещё не устранённая. Пункт удаляется отсюда, когда закрыт
(запись о закрытии — в [progress.md](progress.md)). Статус: **проверено** — подтверждено чтением
кода; **гипотеза** — найдено сканированием, перед работой перепроверить.

## Ожидают подтверждения (продуктовое решение или ломающее изменение)

- **CLI: устаревший ключ `--srcDir` у `format`** (`cli/FormatCommand.java`, `TODO delete old key`).
  Удаление ломает скрипты пользователей. У `analyze` основным ключом остаётся `--srcDir`, так что
  «старый» он только для `format` — нужно решить, какой ключ каноничен для обеих команд.
- **Отчёт JSON: поле `covlocData`** (`context/MetricStorage.java`, `@Deprecated`). Входит в формат
  отчёта, который читают внешние инструменты; удаление — изменение контракта.
- **Значение `-c` различается между подкомандами**: `analyze` применяет файл к глобальной и
  workspace-конфигурации, `lsp`/`websocket`/`mcp` — только к глобальной, у `format` ключа нет
  (гипотеза). Унификация меняет поведение CLI.
- **`LanguageServerConfiguration.update` с битым файлом не бросает** (ADR-0002): утвердить или
  вернуть исключение для явного `update`, оставив терпимость только загрузке при старте.
- **Правки `CLAUDE.md`** по итогам раундов — по правилам репозитория только с согласия мейнтейнера:
  - `reporters/CLAUDE.md`: у `ReportContext` появилось поле `workspaceDir` (раунд 7);
    `AbstractDiagnosticReporter` больше не даёт доступа к `ServerContextProvider` (раунд 26);
  - `configuration/CLAUDE.md`: порядок поиска файла конфигурации теперь живёт в
    `ConfigurationFiles` (раунд 1) — стоит сослаться на него; включение supplier'а проверяет не
    `XxxConfiguration.supplierIsEnabled(...)`, а `SupplierParameters.isEnabled` (раунд 15);
  - `references/CLAUDE.md` и `types/CLAUDE.md`: finder'ы `Keyword`/`NewExpression`/`PlatformMember`
    живут в `types.references`, индексатор спрашивает систему типов через `WorkspaceNames`
    (раунд 29, ADR-0003).
  - `diagnostics/CLAUDE.md`: в таблицу базовых классов — `AbstractComplexityDiagnostic`
    (раунд 39).
  - корневой `CLAUDE.md`: `ReferenceIndex` перечислен среди `@WorkspaceScope`-бинов, а это
    синглтон; per-workspace — его репозитории (найдено в раунде 49).
  - корневой `CLAUDE.md`: «`./gradlew check` — test + jacoco + spotless + javadoc» неверно —
    `check` задачу `javadoc` не запускает (её гоняет отдельный workflow `javadoc.yml`); проверять
    javadoc нужно явно (`./gradlew javadoc`). Найдено в раунде 43.

## Высокий приоритет (дефекты или вероятные дефекты)

- **Сетевые режимы открыты всем интерфейсам без проверки источника — решение мейнтейнера**
  (проверено, раунд 49). `websocket` и MCP поверх HTTP слушают `server.port` (8025), а
  `server.address` нигде не задан — Spring Boot привязывается ко всем интерфейсам; документация
  при этом пишет `ws://localhost:8025/lsp`. Аутентификации нет, `Origin` у WebSocket не
  проверяется (`websocket/WebSocketConfiguration`). Следствие: к серверу может подключиться любой
  узел сети или страница в браузере пользователя (cross-site WebSocket) и через LSP/MCP читать
  файлы рабочей области. Варианты: `server.address=127.0.0.1` по умолчанию (ломает намеренный
  удалённый доступ — нужна явная опция), проверка `Origin`, токен в URL/заголовке. Меняет
  поведение по умолчанию.

- **Нет статического анализа потокобезопасности** изменяемого состояния синглтонов (Error Prone
  или SpotBugs). Ломает сборку на существующем коде — требует решения мейнтейнера.
- **Разделители путей в отчётах**: `GenericIssueReporter`, `TSLintReporter`, `JUnitTestSuites`
  пишут разделители ОС, `CodeQualityReporter` — `/`. Смена — изменение формата вывода на Windows,
  требует решения.
- **Поля `serverPort`/`endpointPath`/`--mcp-path` у команд не читаются** (гипотеза): значения
  берёт Spring из сырых аргументов, поля нужны picocli для справки и приёма опций. Дефолты
  `8025`/`/lsp` в описаниях опций дублируют `application.properties`.

- **Параметр диагностики в абстрактном предке не настраивается общим путём** (проверено):
  `DiagnosticHelper.configureDiagnostic` ищет поле через `getClass().getDeclaredField`, а
  `DiagnosticParameterInfo` собирает параметры и у предка. Живого дефекта нет (единственный такой
  предок, `AbstractMultilingualStringDiagnostic`, переопределяет `configure`); исправление —
  поиск поля по иерархии классов, когда появится второй случай.

## Кеширование и владение состоянием (обзор раунда 49)

Проверено чтением кода; исправленное — в progress.md (раунды 51–54).

- **`ReferenceIndexFiller.filled` — один набор на все рабочие области** (класс — синглтон, а
  данные индекса — per-workspace репозитории). Удаление рабочей области A стирает отметки B;
  если регистрация типов B закончится позже, документы B не получат повторной индексации
  self-членов до правки. Узкая гонка multi-root. Исправление — набор на `ServerContext`
  (тест на две рабочие области).
- **`BslContextHolder` не перечитывает синтакс-помощник при смене `v8platform.binPath`** (нужен
  перезапуск); построенные на нём кеши (`FormParametersResolver`, `EventHandlerResolver`) тоже не
  сбрасываются. Нужно решить, поддерживать ли смену пути на лету.
- **`TestSourcesProvider` — `@Cacheable` по `configurationRoot`, значение зависит от
  per-workspace конфигурации**; у OneScript-областей корень `null` — одна запись на все.
- **Три механизма сброса per-URI данных** (`AbstractDocumentLifecycleClearableIndex`,
  `AbstractOScriptLazyIndex`, ручные карты) — **рассмотрено (раунд 58), слияние отклонено**:
  смысл разный — немедленный сброс по любому событию жизни документа; ленивая сборка с
  переиндексацией по правке и полным сбросом при изменении определения аннотации; данные,
  переживающие закрытие и освобождение документа (объявленные типы, регистрации модулей).
  Дефекты раундов 51–53 были пропущенными обработчиками удаления, а не следствием трёх баз —
  исправлены по месту. Общее правило ArchUnit «у карты по URI есть обработчик удаления» дало бы
  много ложных срабатываний: часть карт — по URI рабочих областей (наблюдатели, MCP), часть —
  локальная (поиск компонент связности, статистика).
- **Мелкое:** `TypeRef.PLACEHOLDER_CACHE` — статическая неограниченная карта по любому имени
  типа; `MethodReturnTypeIndexer.dependentsByUri` оставляет пустые наборы удалённых URI.

## Обработка ошибок, журнал, конфигурация (обзор раунда 49)

- **Sentry не видит большинства сбоев** (решение мейнтейнера): `SentryAspect` — `@AfterThrowing`
  на методах LSP-сервисов, а они возвращают `CompletableFuture`; исключение провайдера
  возникает внутри future и совету не видно; логback-аппендера Sentry нет. Кандидат — хук
  `whenComplete` в `onDocument`.
- **Ожидание `Future` с оборачиванием в `IllegalStateException`** — 5 мест
  (`FormatCommand`, `AnalyzeCommand`, `AnalyzeProjectOnStart`, `ServerContext`,
  `DefaultDiagnosticComputer`) — **рассмотрено и отклонено (раунд 57)**: политика у всех одна
  (флаг прерывания восстанавливается, сообщение — своё для операции), цепочка причин в стеке
  сохраняется; общий помощник дал бы лишь формальное единообразие.
- **Преобразование URI → `Path` без единой политики** — пять охраняемых мест с разными наборами
  исключений и четыре неохраняемых `Path.of(uri)`; канонический `Absolute.path` уже есть.
- **Загрузчики встроенных ресурсов** (`types/registry`) по-разному реагируют на одну ошибку
  (WARN/ERROR, перехват `RuntimeException` только в `BuiltinQueryTables`, свой
  `getResourceAsStream` в обход `BuiltinResources.open()`).
- **Уровни журнала сбоя вывода типа** разные в одном классе (`ExpressionTypeInferencer`: ERROR со
  стеком на горячем пути в пяти местах, DEBUG — в шестом и в соседних компонентах).
- **Замеры времени мимо `MeasuresAspect`** — `ServerContext.millisSince`,
  `ConfigurationTypesProvider`, `MethodReturnTypeIndexer`; два разных часа для одной операции.
- **Конфигурация:** имя файла сведено к `ConfigurationFiles.DEFAULT_FILE_NAME` (раунд 58);
  наблюдатель за файлами при незаданном файле узнаёт новый файл по имени по умолчанию, а не по
  `app.configuration.path` (переопределённый путь, файл создан после старта — не подхватится);
  два выключателя одной возможности
  (`app.platform-context.enabled` и `v8platform.enabled`); `--mcp-path` у двух команд читается
  только для журнала, действует значение из сырых аргументов; `TestRunnerAdapter` повторяет
  `TestRunnerAdapterOptions.getExecutableForCurrentOS()`, тайм-аут 10 с и кодировка `cp866`
  зашиты.
- **Мёртвые настройки журнала** в `application.properties` (hibernate, hikari, JPA, Spring Data —
  таких зависимостей нет).

## Дублирование реализаций (канонизация)

- **`safeGetAst` с перехватом любого `RuntimeException`** (`FormExpressionInference`,
  `PropertyMethodInference`) — после раунда 25 остались две копии второй политики; сузить до
  `findAst()` можно только решением владельцев `types/` (сейчас скрываются и настоящие ошибки).
- **Рассмотрено и отклонено**: объединение `isIdentChar`/сканирования префикса идентификатора
  (`TypeService`, `CompletionProvider`) и `getVariableName` (диагностика и `utils`) — трёхстрочные
  фрагменты с разными результатами, общий хелпер дал бы лишь формальное единообразие; снятие
  кэширования `isVsCodeLikeClient` в двух code lens-классах — снимок на `initialize` осознанный и
  покрыт тестами, выигрыш ~25 строк.
- **Рассмотрено и отклонено (сканирование `diagnostics/`, раунды 34–40)**: пары двух-трёхстрочных
  предикатов — «общий модуль с повторным использованием» (`CachedPublic`,
  `CommonModuleNameCached`; `RedundantAccessToObject` проверяет ещё и `DONT_USE` — другой смысл),
  «последний оператор модуля» (`BeginTransactionBeforeTryCatch`, `CommitTransactionOutsideTryCatch`),
  «присваивание переменной» (`AbstractMagicValue`, `IncorrectUseOfStrTemplate`), «`+1` для
  остальных узлов» (`OneStatementPerLine`, `FieldsFromJoinsWithoutIsNull`), шаблоны имён
  `Вставить`/`Добавить`/`НачатьТранзакцию` (часть с `find()`, часть с `matches()` — разный смысл);
  перегрузка `RelatedInformation.create` по узлу дерева (16 мест разной формы). Общий помощник
  дал бы лишь формальное единообразие.
- **`format` без найденных файлов** завершается с кодом 1 без сообщения.
- **Таблицы «тип токена → `Keywords.MultiName`»** — 3 копии (completion, formatter, diagnostic),
  но назначение разное: у диагностики — допустимые написания (с вариантами `EACH_LO`, `OR_UP`,
  препроцессорными символами, `Истина`/`Ложь`/`Неопределено`), у форматтера — каноническое
  написание с режимом верхнего регистра для `И`/`ИЛИ`/`НЕ`, у completion — предлагаемый набор.
  Слияние в одну таблицу — не чистое устранение дубля (рассмотрено, раунд 46).
  **Ожидает решения:** форматтер приводит к каноническому виду `Асинх`/`Ждать`
  (`ASYNC_KEYWORD`/`AWAIT_KEYWORD`), а `CanonicalSpellingKeywordsDiagnostic` их не проверяет —
  `асинх` не даёт замечания. Добавление — новые срабатывания у пользователей.
- **Мелкие пары копий — рассмотрено и отклонено**: `stringField` (двухстрочный разбор поля в двух
  загрузчиках JSON `types/registry`) и `key` (нижний регистр с `Locale.ROOT`) — связывать ради
  них классы дороже, чем держать копии. (`ProfileKey` закрыт в раунде 48.)
- **Реестры supplier'ов code lens / inlay hint / command** — бины «карта по id» и «регистрация
  подтипов Jackson» в трёх конфигурациях похожи, но это 3–4 строки типизированной Spring-обвязки
  на бин; общий генерик-помощник сэкономил бы ~6 строк на конфигурацию ценой сложности типов —
  рассмотрено и отклонено (`getId()` и разбор нагрузки уже общие, раунды 27–28).
- **Отбор включённых supplier'ов** — у code lens prototype-бин с сортировкой по `@Order`, у
  inlay hint — фильтр в провайдере без сортировки (толкование параметров уже общее, раунд 15).
- **Чтение возможностей клиента** — четыре способа (кэш в holder'е, чтение на каждый вызов,
  из `InitializeParams` события, напрямую); дубли `isVsCodeLikeClient` (понижение
  `LocationLink → Location` уже общее, раунд 31). Связанное: «обновить фичу на событие» реализовано в каждом
  провайдере отдельно (code lens, inlay hints, semantic tokens, diagnostics) — после раундов
  22–23 набор событий выровнен, но механизм остаётся четырьмя копиями; кандидат на общий
  компонент обновления клиента — **рассмотрено и отклонено (раунд 48)**: общим остаётся только
  каркас «обработчик события → `refresh`» (~5 строк на событие), а содержательное — какие события
  нужны фиче и почему (это и записано в javadoc обработчиков) — у каждого провайдера своё; общий
  компонент добавил бы косвенность и оторвал обоснование от владельца.
- **Ответ на запрос к неизвестному документу — решение мейнтейнера** (проверено): часть списковых
  запросов отвечает `null` (`codeAction`, `documentSymbol`, `foldingRange`, `documentLink`,
  `formatting`…), часть — пустым списком; `definition` — `Either.forRight`, `implementation` —
  `Either.forLeft`. Оба варианта допустимы спецификацией, но правила нет. Предложение по LSP 3.17:
  `null` везде, где тип результата допускает `null`; пустое значение — только там, где не
  допускает (`documentColor`, `colorPresentation`, `textDocument/diagnostic` — так уже сделано).
  Правило живёт в одном месте — ответе `ifMissing` у `onDocument` (раунд 16). Меняет видимое
  клиенту поведение. Отдельно: порядок аргументов провайдеров `(params, doc)` vs `(doc, params)`.
- **Имя рабочей области** выводится в двух местах (`AnalyzeCommand` — из `Path`,
  `ServerContextProvider` — из URI); для каталогов результат одинаков, выигрыш от слияния мал
  (нормализация URI от MCP-клиента сведена в `McpWorkspaceFolders`, раунд 30).
- **Язык сообщений интерфейса — решение мейнтейнера** (проверено): ключ `language` читается и в
  глобальную, и в workspace-конфигурацию. Сообщения хода работы (`ServerContext.getMessage`,
  `MethodReturnTypeIndexer`) берут глобальный язык, уведомление Sentry (`SentryAspect`) — язык
  рабочей области, если она есть, иначе глобальный; диагностики и прочее — язык рабочей области.
  Если `language` задан только в файле рабочей области, ход работы показывается на одном языке,
  а диагностики — на другом. Нужно решить, что управляет языком сообщений сервера, и свести
  правило в одно место. Там же: `GlobalLanguageServerConfiguration.reset()` повторяет дефолты
  вручную вместо снимка, как у workspace-конфигурации.
- **Дефолты опций в документации** (`ConfigurationFile.md`, обе локали) не сверяются
  автоматически; код ↔ схема сверяет `ConfigurationSchemaDefaultsTest` (раунд 17).
